# Architecture

`attend-server` is a **modular monolith**: one deployable Loco application, one Postgres
database, and business code split into modules with enforced boundaries. A module can later
be extracted into its own service because it already owns its data and talks to others only
through a small public API and events.

## Modules

Listed from the lowest layer to the highest. **A module may only depend on modules above it
in this list.** Nothing depends upwards.

| Module | Postgres schema | Tables | Responsibility |
|---|---|---|---|
| `calendar` | `calendar` | `terms` | Academic terms |
| `identity` | `identity` | `users`, `devices`, `device_lifecycle_items` | Accounts, login, device binding and rebinding |
| `courses` | `courses` | `courses` (with the `policies` jsonb column), `course_members` | Courses, rosters, attendance policy of a course |
| `capture` | `capture` | `rooms`, `nfc_tags`, `class_sessions`, `scan_events` | Scheduling, receiving and verifying taps |
| `records` | `records` | `attendance_records`, `attendance_record_lifecycle_items`, `appeals`, `appeal_lifecycle_items` | Statuses, history, manual changes, appeals |

```
calendar  <-  identity  <-  courses  <-  capture  <-  records
```

`calendar` exists on its own so that `identity` (device validity per term) and `courses`
(a course belongs to a term) can both depend on terms without depending on each other.

## Rules

1. **Dependency direction.** Enforced by `tests/architecture.rs`, which fails the build.
2. **Private internals.** Inside a module, everything except `api.rs` is private (`mod x;`, not
   `pub mod`). The compiler then stops other modules from using it. Only `api.rs` and
   `routes()` are public.
3. **Code is grouped by feature.** Inside a module, a folder per feature (such as `auth/` and
   `account/` in `identity`) with the same file names in each: `controller.rs` (HTTP
   handlers), `dto.rs` (request and response shapes and their validation), `service.rs` (the
   logic), plus `token.rs`/`extractor.rs`-style files only when a feature needs them.
   `entities/` is generated from the database and never edited; `errors.rs` holds the
   module's error constructors. A module that has no feature yet is just `mod.rs`, `api.rs`
   and `entities/`.
4. **Public API is deliberate.** `api.rs` lists what other modules may call. Needing
   something else is a design conversation, not a quick `pub`.
5. **One owner per table.** Only the owning module's code reads or writes its tables. Other
   modules ask through its `api`.
6. **Schemas.** Each module owns one Postgres schema, created by its first migration.
7. **References across modules are plain IDs.** No foreign keys and no joins across schemas.
   Check that the referenced row exists through the owning module's `api`. Foreign keys inside
   a module are fine.
8. **Side effects across modules go through events**, published with the outbox pattern, and
   handlers must be idempotent. Reads go through `api`.
9. **Primary keys are UUID v4**, generated by the database (`gen_random_uuid()`).
10. **Time comes from the clock.** Code that depends on "now" takes a `shared_lib::clock::Clock`.

## `shared_lib`

Small, stable code every module may use: the event `Envelope`, the `Clock`, the API error
envelope, and the typed `CoursePolicies` contract. It depends on **no module**, holds no
business rules, and changes there need review from every team.

## Authentication (`identity`)

Clients sign in with `POST /api/auth/sign-in` (email and password) and send the returned signed
token (JWT, HS256) as `Authorization: Bearer <token>` on later requests. The token carries only
the account id, when it was issued and when it expires, both taken from the `Clock`. The
signing secret and the lifetime are `auth.jwt` in `config/*.yaml`; in production the secret comes
only from the environment variable `JWT_SECRET`. Handlers that need a signed-in user take the
`identity` module's authentication extractor, which answers with the `ApiError` envelope.
Details: `specs/identity/sign-in/requirements.md`.

## Policy edit guard (design, not built yet)

`courses` owns `policies` but cannot know about sessions without depending on a lower layer
the wrong way round. So `courses` defines a port, a trait with two steps:

- `veto(course)`: read-only check; any veto rejects the edit with `409`.
- `prepare(course)`: may write, for example finalise ended sessions.

`capture` implements the veto ("a session is open"), `records` implements the preparation
("finalise ended sessions with the old policy"). `app.rs`, the one place allowed to know
everyone, registers them. `courses.set_policies` runs all vetoes, then all preparations, then
saves, in one transaction with the course row locked.

## Events (design, not built yet)

| Event | From | To | Purpose |
|---|---|---|---|
| `ScanAccepted` | `capture` | `records` | Create or move the attendance record |
| `RosterChanged` | `courses` | others | Refresh anything derived from the roster |

Delivery is an in-process bus backed by an `outbox` table: the business change and the event
row commit together, and a dispatcher loop runs the handlers, retrying failures. Events carry
a snapshot so consumers never need to call the producer back.

## Adding a table to a module

This procedure was verified against Loco and Postgres. Use it for every table.

1. **Spec first.** The table follows from a requirement in `specs/` and the ER diagram.
2. **Schema test first.** Add the test to `tests/schema.rs` (it must fail: the table does not
   exist yet). Tests that boot the app and touch the database must be `#[serial]`, because they
   share one test database.
3. **Migration as plain SQL, forward-only.** In `migration/src/<module>/` add two files and list
   the Rust one in that folder's `mod.rs`:

   ```
   m<yyyymmdd>_<nnnnnn>_<what>_<module>.rs      # copy an existing wrapper
   m<yyyymmdd>_<nnnnnn>_<what>_<module>.sql
   ```

   The migration name must be unique across modules. There is **no `down`**: migrations only go
   forward, and never edit one that has been merged. A mistake is fixed by a new migration. Write
   the DDL by hand: schema-qualified
   table, UUID key with a database default, `timestamptz` columns, and the trigger that keeps
   `updated_at` correct:

   ```sql
   CREATE TABLE calendar.terms (
       id         uuid        PRIMARY KEY DEFAULT gen_random_uuid(),
       name       text        NOT NULL UNIQUE,
       created_at timestamptz NOT NULL DEFAULT now(),
       updated_at timestamptz NOT NULL DEFAULT now()
   );
   CREATE TRIGGER set_updated_at BEFORE UPDATE ON calendar.terms
       FOR EACH ROW EXECUTE FUNCTION public.set_updated_at();
   ```

   Value sets are `text` with a `CHECK`. References to another module's rows are plain `uuid`
   columns with a comment naming the table, never a foreign key. Do not use
   `cargo loco generate model`: it assumes integer ids and the default schema.
4. **Entity.** Apply the migrations to a database, then generate the entities for that schema
   only:

   ```
   sea-orm-cli generate entity \
     --database-url postgres://loco:loco@localhost:5440/attend_server_development \
     --database-schema <module> --with-prelude none -o src/modules/<module>/entities
   ```

   The result carries `schema_name = "<module>"`, `Uuid` keys and `DateTimeWithTimeZone`
   columns. The command rewrites `entities/mod.rs`: put back the header and
   `#![allow(dead_code)]` that the other modules have (until the first model uses the entities,
   unused entities otherwise fail `clippy -D warnings`). Never edit the generated files.
5. **Green.** `cargo test` passes, including the new schema test.

## Test database

`config/test.yaml` applies pending migrations on boot, then empties every table of every module
schema (`modules::truncate`), so each run starts with no data. It deliberately does **not** use
`dangerously_recreate`: Loco implements that with SeaORM's `fresh`, which only drops tables in
the default schema, so with a schema per module it fails with "relation already exists".
Migrations are forward-only and append-only. A migration that was merged is never edited, and
there is no way to revert one (`tests/schema.rs` checks that a revert is refused). If a local
database ends up half-migrated, reset it with `docker compose down -v && docker compose up -d`.

## Authentication configuration

Access tokens are JWTs (HS256) signed with `auth.jwt.secret` (base64) and valid for
`auth.jwt.expiration` seconds (86 400, 24 hours). `development` and `test` use a fixed local
secret; `production` reads `JWT_SECRET` from the environment with no default. The `Clock` that
tokens are issued and checked with lives in Loco's shared store (installed by
`initializers::clock`; the Cucumber harness replaces it with a `FixedClock`).

## Adding a feature to a module

1. Write the spec and the `.feature` file first (`docs/development-process.md`).
2. Create a folder in the module for the feature (for example `src/modules/identity/auth/`),
   with a `mod.rs` that declares its files and a `routes()` for its endpoints.
3. Add what the feature needs, using the same file names as the other features:
   `controller.rs` (handlers), `dto.rs` (request/response shapes and validation) and
   `service.rs` (the logic). Add `token.rs`, `extractor.rs` or similar only when the feature
   really has that concern. New error codes go in the module's `errors.rs`.
4. Register the routes in the module's `mod.rs` (`routes()`), declare the folder there as
   `mod <feature>;` and keep it private.
5. Write the steps in `tests/steps/<module>.rs`, and unit tests next to the code.
