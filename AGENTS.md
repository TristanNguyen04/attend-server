# Agent guide for `attend-server`

The backend of the SUTD NFC attendance system: a **modular monolith** on
[Loco](https://loco.rs) (Rust, SeaORM, Axum, Postgres). Prefer Loco's built-ins and generators
over adding crates or wiring infrastructure by hand.

## Read first

| File | Why |
|---|---|
| `constitution.md` | The rules: specs, scenarios and tests ship together; CI is the gate |
| `docs/development-process.md` | The flow (spec, scenarios, tasks, build) and commands |

| `docs/er-diagram.md` | The approved data model |

## Layout

```
src/app.rs              # Loco hooks: aggregates each module's routes, workers, tasks (no business logic)
src/modules/<module>/   # calendar, identity, courses, capture, records
    mod.rs, api.rs      # the only public surface of a module
    controllers/ dtos/ entities/ handlers/ models/ workers/   # private to the module
src/shared_lib/         # events envelope, clock, error envelope, policies contract
migration/src/<module>/ # each module's migrations as .rs + .sql, forward-only; migration/src/lib.rs concatenates them
config/*.yaml           # per-environment config (LOCO_ENV); secrets come from the environment
specs/<module>/<feature>/   # requirements.md + tasks.md (SDD)
tests/features/<module>/    # Gherkin scenarios; steps in tests/steps/
tests/architecture.rs   # fails the build if module dependencies point the wrong way
tests/schema.rs         # the data model as Postgres stores it (keys, value sets, constraints)
```

## Module rules (details in `docs/architecture.md`)

- Dependencies only point down: `calendar < identity < courses < capture < records`.
- A module's internals are private. Other modules use only its `api.rs`.
- Only the owning module touches its tables. Across modules, reference rows by **ID only**:
  no foreign keys and no joins across schemas.
- Cross-module side effects go through events (outbox). Handlers are idempotent.
- `shared_lib` depends on no module and holds no business rules.
- Primary keys are **UUID v4**, generated by the database. This differs from Loco's default
  integer ids, so write migrations by hand (plain SQL files) instead of using generators.
- Never hand-edit files in `entities/`: they are generated from the migrated database.
- **Migrations are forward-only**: no `down`. Never edit a merged migration; fix a mistake with a
  new one.
- Foreign keys exist only inside a module. A new table follows `docs/architecture.md`
  ("Adding a table to a module"): schema test first, then the migration, then the entity.

## How to work

1. Follow `docs/development-process.md`: spec, scenarios, tasks, then build a task or the whole
   feature in one go (code, steps and unit tests together). We dropped the strict red/green
   loop because it was way too slow for the project. Do not merge on a failing test.
2. Specs change only through a human-reviewed commit. If a requirement is unclear, ask; do
   not guess.
3. No breaking changes to existing endpoints.
4. Errors use the `ApiError` envelope (`shared_lib::error`): `{ code, message, details }`.
5. Anything that depends on the current time takes a `Clock`. Never sleep in tests.
6. Start Loco files with `use loco_rs::prelude::*;` and return `loco_rs::Result<T>`.
7. Config is YAML in `config/`; read secrets with the `get_env` helper. No secrets in code,
   config files, logs or commit messages.

## Git rules

- **Never push to `main`.** Work on a branch and open a pull request.
- Do not commit or push unless the user asks.
- Use the skills below for committing and for pull requests.

## Commands

```
docker compose up -d                          # local Postgres
cargo test                                    # unit + architecture + Cucumber
cargo test --lib | --test cucumber | --test architecture
cargo fmt --all
cargo clippy --all-targets -- -D warnings
cargo loco start                              # run the app
cargo loco routes                             # list routes
```

## Skills

- `/commit-and-push`: check, commit and push the current branch.
- `/create-pull-request`: open a pull request for the current branch.

## What checks cannot tell you

Passing tests show the specified behaviour works, not that the specification is right. When
reporting, say which checks you ran, which you did not, and what is still unverified.
